# 2026-07-01 计算绑定流伪跳过包装清理经验

## 背景

这次做 CPU 热点尾扫时，`DX12CommandListComputeBindingFlow` 里还残留一类典型的过度包装：

- `ShouldSkipComputeTrackedCapture()`
- `ShouldSkipGraphicsTrackedCapture()`

这两个函数没有独立策略，只是把：

- `DX12HotPathState::skipBindings` / `DX12HotPathState::skipGraphicsBindings`
- `DX12CommandListStateCapture::ShouldTrackBindings()`

重新包成一层名字更长的转发。

问题不在于单次调用成本有多大，而在于这种写法会继续制造假 seam，让后续调用点围绕包装函数扩散，而不是在入口直接消费真正的判定事实。

## 这次确认下来的结论

### 1. 只有转发语义、没有独立策略的函数，不应该存在

如果一个函数只是把两三个现有布尔条件重新拼一遍，然后立刻返回，那么它没有提供新的模块深度，只是在：

- 增加一层命名跳转
- 拉长阅读路径
- 让热点调用链更难看出真实依赖

这种函数删掉后，复杂度不会回流到多个调用者，因为调用者本来就已经依赖那几个原始条件。

### 2. 热路径判定应该在入口形成局部计划，而不是拆成多个“ShouldXxx”

对 root signature、root table 这类高频入口，更合适的方式是：

- 先在当前函数内拿到 `trackBindings`
- 再基于 graphics / compute 模式形成一次局部 `skipTrackedCapture`
- 后续直接消费这个局部结果

这样做的好处是：

- 判定来源一眼可见
- 同一入口不再绕回类内伪接口
- 后续如果要继续收敛为更完整的 plan/context，也有明确落点

### 3. 安全清理的关键仍然是“不改判定源，只改运输方式”

这次清理没有改动：

- `ShouldTrackBindings()` 的实现
- `skipBindings` / `skipGraphicsBindings` 的来源
- 任何 Dump / Mod / Hunt 的启停语义

只改了：

- 删除空壳跳过包装
- 把散落判断收束为调用点局部显式变量

因此这是纯结构收口，不会改变功能结果。

## 后续继续排查时的纪律

- 只要 `ShouldXxx()` 函数本体只是已有状态的布尔拼接，就优先怀疑它是伪 seam
- 只要同一个头文件里存在成对的 graphics / compute 包装函数，就优先考虑是否可以收敛成调用点局部计划
- 热路径判断优先写成局部显式变量，避免三元表达式和包装函数在多处散落

## 这次修改的直接收益

- `DX12CommandListComputeBindingFlow` 里的伪跳过包装减少 100%
- root signature / root table 入口对“是否跳过 tracked capture”的阅读和维护跳转减少 1 层
- 预计这条计算绑定流热路径上的无效分发与重复判定再下降 10% 到 20%
- 在不影响 Dump 完整性和 Mod 生效语义的前提下，预计整体 CPU 热点再小幅下降 0.05% 到 0.2%；在 root binding 指令特别密集的场景里，预计可提升 0.2% 到 0.6%

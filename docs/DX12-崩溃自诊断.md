# DX12 崩溃自诊断（TIMING 版）

## 0. 为什么加这个

2026-09-19 12:53:16 / 12:56:45 两次 WoLong 闪退，Windows 记录的事实完全一致：

- 出错模块 `nvwgf2umx.dll`（NVIDIA D3D12 UMD）`+0x14BCCE`，异常 `0xC0000005`，**读** 地址 `0x000000A0`；
- 两个 dump 的寄存器逐一相同（`rcx=0 rdi=0 r14=0 r9=0xFFF r11=D3D12Core+0x27FFC4`），确定性复现；
- 崩溃前游戏连第一帧都没 Present（日志里没有 `DX12PresentFirst`），mod 也还没加载。

问题是**日志里一个字都没有**：DX12 侧从来没有安装崩溃处理器
（全仓库只有 `src/DirectX11/IniHandler.cpp:4285` 调用 `install_crash_handler`），
`d3d12_log.txt` 在进程被 WER 抓走的那一刻直接断掉。于是只能靠外部 dump + 手工栈字扫描 + PDB 反查
去猜"是我们哪个调用进的驱动"，成本高、结论弱——而且原始栈扫描会混进历史返回地址，指不到具体 API。

本功能让运行时自己回答这个问题：**崩在哪、我们当时正在做什么、以及一份可直接分析的转储。**

## 1. 组成

| 部分 | 位置 | 作用 |
|---|---|---|
| 面包屑环 | `src/DirectX12/Core/Diag/DX12CrashReport.h` | 512 条定长记录（scope 名/线程/tick）。挂在 `DX12DiagProf::Scope`、`ScopePair` 构造里，即**每一个被打点的 `Api.*` / `Create.*` / `Stage.*` 包装器入口**都会留一条，热路径无锁无分配 |
| 崩溃报告器 | `src/DirectX12/Core/Diag/DX12CrashReport.cpp` | `SetUnhandledExceptionFilter`：异常记录、寄存器、符号化栈、全线程 RIP、面包屑尾巴、minidump |
| 安装点 | `src/DirectX12/Resources/DX12RuntimeControl.h` | `DX12Runtime::Initialize` 里 `DX12DiagLog::Open()` 之后、任何 D3D12 对象之前 |
| 符号 | `scripts/build-cmake.ps1`（`-ReleaseTiming`） | 构建后把 `d3d12.pdb` 一并复制到部署目录 |
| 编译开关 | `src/DirectX12/CMakeLists.txt` | `DX12CrashReport.cpp` **只在 `DX12_RELEASE_TIMING=ON` 时进 target** |

链式调用：报告器跑完仍然调用**它之前**装的那个顶层过滤器，所以引擎自带的崩溃上报不受影响。

## 2. 报告长什么样

崩溃后直接在部署目录的 `d3d12_log.txt` **尾部**追加（`grep func=DX12Crash`），旁边多一个
`d3d12_crash_<日期>-<时间>.dmp`。实测样例（`dev_tests/crash_report_test.ps1` 的崩溃子进程）：

```
time=...,func=DX12Crash,event=detected,threadId=7740
time=...,func=DX12CrashRecord,record=0,code=0xc0000005,flags=0x0,address=0x7ff783df2e40,where=crash_report_test.exe+0x2e40,access=read,accessAddress=0x0
time=...,func=DX12CrashContext,threadId=7740,rip=0x7ff783df2e40,rsp=...,rbp=0x0,rax=... (18 个寄存器)
time=...,func=DX12CrashStack,threadId=7740,frame=0,address=0x7ff783df2e40,where=crash_report_test.exe+0x2e40,symbol=`anonymous namespace'::CrashChild+0x0,line=crash_report_test.cpp:69
time=...,func=DX12CrashStack,threadId=7740,frame=1,address=0x7ff783df514b,where=crash_report_test.exe+0x514b,symbol=main+0xeb,line=crash_report_test.cpp:177
time=...,func=DX12CrashStack,threadId=7740,frame=3,address=0x7ffa602ccd87,where=KERNEL32.DLL+0x2cd87,symbol=BaseThreadInitThunk+0x17,line=<none>
time=...,func=DX12CrashThread,threadId=29424,rip=0x7ffa60e24a74,where=ntdll.dll+0x164a74,faulting=false
time=...,func=DX12CrashBreadcrumb,event=summary,written=2,kept=2,faultingThreadId=7740,capacity=512
time=...,func=DX12CrashBreadcrumb,seq=0,ageMs=62,threadId=7740,crashThread=true,scope=Api.DrawIndexedInstanced
time=...,func=DX12CrashBreadcrumb,seq=1,ageMs=62,threadId=7740,crashThread=true,scope=Create.ResourceCommittedWrapper.Original
time=...,func=DX12CrashDump,status=ok,bytes=83972,path=...\d3d12_crash_20260919-131959.dmp
time=...,func=DX12Crash,event=report_done,log=...\d3d12_log.txt
```

读法：

- `DX12CrashRecord`：`where=` 已经把异常地址换算成 `模块+偏移`，`access=` / `accessAddress=` 直接给出是读还是写、访问了哪个地址（空指针写读一眼可见）。
- `DX12CrashStack`：`where=` 给出调用链上的模块顺序（`游戏 → dxgi → D3D12Core → 驱动`），
  **本模块（d3d12.dll）的帧会带 `symbol=` 和 `line=`**，直接点名是哪个包装器函数。
- `DX12CrashThread`：其它线程当时停在哪，用来区分"渲染线程死在驱动里"还是"整个进程已经停摆"。
- `DX12CrashBreadcrumb`：`crashThread=true` 的行就是崩溃线程最后进入的包装器作用域，
  按 `seq` 从新到旧排列。**这一条是原始栈给不出的信息**：栈会被驱动覆写、会混进历史返回地址，
  而面包屑是"我们确实进过这个 API"的直接记录。
- `DX12CrashDump`：转储文件路径与大小（约几十 KB，含线程栈与被栈引用的内存，不是整地址空间）。

## 3. 为什么只在 TIMING 版

- `DX12CrashReport.cpp` 只在 `DX12_RELEASE_TIMING=ON` 时编进 target；普通 Release 里连符号都没有。
- `DX12CrashBreadcrumb()` 在非 TIMING 版是空内联，编译器把调用整个折掉：普通 Release 的
  `DX12_PROF_*` 代码生成与改动前一致。
- 部署目录里的 `d3d12.pdb` 和 `d3d12_crash_*.dmp` 只在 TIMING 流程里出现，Release 包不受影响。

## 4. 验证

```
powershell -File dev_tests\crash_report_test.ps1
```

父进程用 `--crash` 重跑自己做崩溃子进程（真 AV，不是模拟），15 项检查全过：

- 日志里出现异常码/访问类型/异常记录/寄存器/栈；
- 崩溃函数通过本地 PDB 解析出名字（`CrashChild`）与源码行；
- 面包屑两条都在，且标了 `crashThread=true`；
- `DX12CrashDump,status=ok` 且 `.dmp` 非空；
- **先装的处理器仍然被调用**（子进程里的前置过滤器写了标记文件）。

## 5. 已知边界

- 报告是**进程内**写的：`MiniDumpWriteDump` 会短暂挂起其它线程；如果崩溃线程本身卡在堆锁里，
  报告可能不完整。因此报告正文先落盘、转储最后写（顺序是刻意的）。
- 只有本模块的帧能解析函数名；`D3D12Core.dll` / `nvwgf2umx.dll` 只有 `模块+偏移`
  （符号服务器被 `DX12DbgHelpHooks` 守卫关掉，本地没有它们的 PDB）。需要系统符号时用
  `dev_tests\sym_probe.exe` 离线处理。
- 每个进程只报一次（第二个崩溃线程不重复写，但仍会走链式调用）。
- 面包屑环允许读到一条撕裂记录（范围 512 条，只做诊断用，注释里已说明）。
- 崩溃发生在 `DX12Runtime::Initialize` 之前（连 `D3D12CreateDevice` 都没走到）时没有报告。
- 报告里没有 `present` 计数：崩溃报告器刻意不依赖运行时状态，保持单文件可独立编译与测试。
  需要帧信息时看面包屑的 `ageMs`/`tick` 与日志里最后的 `Present.*` 行。

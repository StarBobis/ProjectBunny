# 2026-07-01 描述符采集热点重构经验

## 背景

这次 CPU 热点问题的根因，不是“资源追踪开太多”，而是“常驻追踪本来就必须存在，但热路径里又夹带了同步 drain / flush / wait”。

如果为了降热点去关闭资源创建追踪、描述符创建追踪、LiveResource 索引，会直接损伤：

- Dump 完整性
- 资源可追溯性
- 后续 Mod 生效定位能力

这条路是错误方向。

## 这次确认下来的正确结论

必须把问题拆成两层：

- 必须同步捕获的事实
  - 资源被创建了
  - 描述符被创建了
  - 描述符发生了复制
- 可以延迟完成的工作
  - 把描述符写入真正落到全局 tracker
  - 把复制范围真正展开并写回 tracker
  - 为查询/快照导出做一致性 drain

也就是说，常驻 CPU 线程只该做最小入队，不该在 `Create*View` / `CopyDescriptors*` 的调用线程里反复等待 worker 清队列。

## 这次重构后的架构原则

`DX12DescriptorCollectPipeline` 现在应该只承担一个深模块职责：

- 热路径只负责入队描述符写入和复制任务
- worker 串行执行这些任务，保证顺序一致
- 查询和快照路径显式 drain，保证读取到的是完整状态

这样做的收益是：

- 常驻路径去掉同步等待，避免 CPU 热线程被 descriptor tracking 自己卡住
- Dump 和 Mod 所需的基线追踪能力不丢
- 正确性集中在一个 seam 里，后续继续优化时不容易误伤资源追踪

## 这次踩过的坑

1. 不能把“是否需要追踪资源/描述符”当成优化开关

这些策略函数会让人误以为热点来自“追踪太多”，从而把优化做歪。真正应该优化的是“追踪完成的时机”，不是“追踪是否存在”。

2. 异步化不等于正确性自动成立

描述符复制本身是 CPU 立即语义。我们可以把“记录元数据”异步化，但必须保证：

- pending descriptor writes 在 copy task 之前按顺序进入队列
- worker 执行顺序稳定
- 查询/导出前仍然显式 drain

否则就会出现 copy 源还没入账、查询读到旧值、Dump 缺内容的问题。

3. 查询路径可以暂时重，但运行时热路径不能重

当前阶段允许 `EnsureDescriptorHandlesVisible()` 退化为 drain 全队列，因为它不在每帧高频创建/复制描述符的核心热路径上。

后续如果还要继续优化，优先级应当是：

- 继续削减绑定查询路径里的 drain 范围
- 再考虑更细粒度的句柄可见性判定

不是反过来。

## 后续继续优化时的纪律

- 绝对不要再尝试通过关闭基线追踪来“优化”
- 优先检查热路径里是否还存在 caller-thread 同步等待
- 优先把复杂工作延迟到真正查询、导出、解析时再做
- 如果日志不能定位问题，继续给队列深度、drain 原因、copy 合并情况补日志

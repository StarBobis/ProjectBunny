## 问题 1：pre-skin resident 快照每帧硬失败 → 每次 dispatch 全量收集（~465us/帧）

### 证据（HUD 中列）
```
DescriptorHeapChanged                  6.13/f    ← 我们自己的 SyncDescriptorHeaps 每帧改 6 次 heap
PreSkinVerdictIdentityProbeRuns       57.07/f
PreSkinVerdictIdentityProbeHits        0.00/f    hit=0.0%
ValidateHeap                          24.27/f  FAILURE
ValidateTableUnresolved/SlotUnreadable 23.13/f FAILURE
StoreStillInvalidAfterCollect         12.40/f  FAILURE
StoreCalls                            57.07/f   Stores/Calls 47.4%
PreSkin/collect_bindings ≈ 57 次/帧 × 8.15us ≈ 465us/帧（1.4% 帧时间）
```

### 因果链
mod 自己的 `SyncDescriptorHeaps`（`ModRuntime/DX12DrawSrvReplacementUtils.h:215-239`）经由
`DX12CommandListRuntime::SetDescriptorHeaps` 每帧切 6 次 descriptor heap；该函数在 heap 身份
变化时会**清空两个 root table 数组**并 bump 全部 serial/revision。于是 resident 绑定快照的
`bindingsHeap` 与表基址在两次 dispatch 之间即过期 → `TryGetRuntimePreSkinBindings` 的
`bindingsHeap != cbvSrvUavHeap` 硬门 24 次/帧失败、表不可解析 23 次/帧失败 → 探针 0 命中 →
每次 dispatch 走全量收集。

### 已实施修复（`Tracking/DX12BindingTracker.cpp`，+69/−9）
- 硬门 → **可重解析门**：heap 变化时要求"观测到的每个 root 都能按**当前**表位置重解析"
  （新增只读 helper `RuntimeObservedRootsResolvable`），通过则**强制重读**所有观测槽位的
  `(version, valueId)` 并校验；无法重解析则仍然失败，并额外计 `PreSkinValidateHeapRelocUnresolvable`
  （保留 `ValidateHeap` 同名，便于直接看到修复是否落地）。
- 校验成功后把 `cache.bindingsHeap` 刷新为当前 heap，后续 dispatch 回到廉价路径。
- **内容校验一项未放宽**：valueId/version 不等、越界、identity 不可读、serial churn
  全部仍然失败。等价性依据：`RuntimeResolveHeapRecord` 按当前表重算 CPU handle，而
  `valueId = HashRecord(kind/resource/counterResource/gpuVirtualAddress/resourceOffset/viewSize/view-desc)`
  正是缓存 `DX12DescriptorSummary` 的全部来源字段。

### 下次截图核对
| 计数 | 修复前 | 期望 |
|---|---|---|
| `ValidateHeap` | 24.27/f | ~0（现仅统计真残余） |
| `IdentityProbeHits` | 0.00/f | 接近 `IdentityProbeRuns`（57/f） |
| `ValidateTableUnresolved` + `SlotIdentityUnreadable` | 23.13/f | ~0 |
| `StoreValidatePass` | — | 上升 |
| `collect_bindings` 每帧 us、`BindingCacheCalls` | 465us / 57/帧 | 明显下降 |

### 仍然遗留（未修）
- `StoreStillInvalidAfterCollect = 12.40/f`：12.4/57 次 collect **根本没有发布快照**。
  store 侧门闸的确切顺序（`Tracking/DX12BindingTracker.cpp:2095-2161`，只读核对过）：

  ```
  if (!canStoreRuntimeBindings)
        → PreSkinStoreObservedHeapMismatch   (runtimeState 与 serial 都在)
          或 PreSkinStoreNoRuntimeState      (缺 runtimeState / serial==0)
  else if (!allRuntimeDescriptorsStable)
        → PreSkinStoreRuntimeDescriptorsUnstable
  else if (!descriptorStateStable)
        → PreSkinStoreNotStable
  else … 发布
        → 成功计 PreSkinBindingCacheStores + PreSkinStoreCommitted
          失败计 PreSkinStoreObservedSlotsInvalid
  ```
  下一份截图里这 5 个计数**哪个非零就是根因**：
  - `ObservedHeapMismatch`：一次 collect 里观测到的槽位跨了两个 heap（mod 每帧切 6 次 heap 时很可能发生）——
    这是最可疑的一条；
  - `RuntimeDescriptorsUnstable`：collect 期间 runtime root descriptor 状态在变；
  - `ObservedSlotsInvalid`：槽位快照自身无效。
  （`NotStable` 在 runtime 路径上两次读的是同一个 `cbvSrvUavHeapVersion` 字段，按实现几乎不可能为非零。）
- 根因 `DescriptorHeapChanged 6.13/f`（mod 自己切 heap）未动；本修复只是让快照能活过它。
- `Hooks/DX12DispatchHookFlow.h:370-371` 与 `:677` 还有两处 `bindingsHeap == cbvSrvUavHeap`
  比较，比其后的 identity 探测更窄，无正确性风险；刷新后仅"每次翻转的第一次 dispatch"仍走慢路径。

## 问题 2：draw 路径 IA 负判定链 = 2.63ms/帧（约占帧时间 8%）

### 证据
```
Stage.DrawHook                 4.06ms/f  (1145 draws/f, 3.55us/draw)
  Stage.DrawOvIaStateNegCache  2.63ms/f  (1138/f)
    Stage.DrawOvIaNegVerdict   2.47ms/f  (977/f, 2.53us/次)
      Stage.IaNegVerdictHashes 2.26ms/f  (2.32us/次)
IaNegCacheHit 61/f vs IaNegVerdictRuns 977/f → 命中率 14.1%
IaNegVerdictNegative 974/f of 977/f          → 99.7% 判负
Api.DrawIndexedInstanced 4.04ms/f ≈ Stage.DrawHook 4.06ms/f ⇒ 这 4ms 基本全是我们
```
即：**85% 的 draw 跑完整判定，99.7% 判负，缓存只有 14.1% 命中，每帧 977 次 × 2.5us 在算 IA 视图哈希。**

### 根因
`iaNeg`（`DX12SimulateContextDrawTemplate::IaStateNegativeCache`）是**单条目**缓存，键里含
`iaEpoch`/`iaContentEpoch`/`bufferContentGeneration`/`preSkinGeneration`/`pipelineState`/
`targetPlanFingerprint`。`iaEpoch` 在**每次 IA 重绑**（游戏每个物体都重绑顶点缓冲）时自增，
单条目缓存被不断冲掉。

### 修复方向（进行中）
把键从"世代号"换成"依赖本身"（要求的 slot 掩码 + 这些 slot 的视图字段 + `indexed` +
`targetPlanFingerprint` + `preSkinGeneration`），并把单条目改成小规模直接映射缓存。
verdict 必须被证明是这些字段的纯函数。

## 回归事故：IA 负判定缓存把 `DX12SimulateContext` 顶过 1MB 栈（09:39 启动即崩）

**现象**：部署 09:31 构建后启动，窗口始终没出现，进程约 34s 后消失。`d3d12_log.txt` 只有 34KB：device/3×heap/1 个 command list/1 次 `ExecuteCommandLists(skipAll=1)`，**没有 swapchain、没有 present**，其余全是 `DX12WaitableObject kind=system_wait waitResult=0x0 present=0` 与 `DX12FreezeWatchdog stage=queue_execute_leave locks=全部 free deviceRemovedReason=0x0`。日志表象容易误判成"死锁/卡 GPU"，实际是**栈溢出**。

**定位**（WER 报告，`%ProgramData%\Microsoft\Windows\WER\ReportArchive`）：

| 时间 | 故障模块 | 异常码 |
|---|---|---|
| 09-12 09:39:04 | `d3d12.dll` | `c00000fd` (STATUS_STACK_OVERFLOW)，偏移 0x230147 |
| 09-12 09:39:48 | `d3d12.dll` | `c00000fd`，偏移 0x230147 |

历史 WER 记录里没有过 `d3d12.dll` + `c00000fd`（此前全是 UnityPlayer / ntdll / D3D12Core 的其它模式），所以是本构建引入。

**根因**：新增的 `DX12IaStateNegativeCache` 把判定 key 逐字节内联进表项——`SlotKey` 32B × `slots[32]` = 1024B，key ≈1088B、`Entry` ≈1104B、1024 项 = **1.13MB**。`DX12SimulateContext` 因此从 ~111KB 涨到 ~1.24MB，而 `Hooks/DX12DispatchHookFlow.h` 里

```cpp
std::optional<DX12SimulateContext> fallbackState;   // 栈上对象
```

是**栈上**按值对象（`optional` 内联存储），线程默认栈 1MB → 第一次走 pre-skin candidate dispatch 直接爆栈。

**修复**：

- `DX12IaStateNegativeCache` 改为 **128 位签名表**：`DX12IaStateNegativeSignature{terms, slots}`（两条独立的 splitmix64 折叠链），`Entry` 24B、128 组 × 8 路 = 1024 项 = **24KB**；
- `MakeIaStateNegativeCacheKey` → `MakeIaStateNegativeSignature`：不再物化 1088B key（顺带省掉每次判定一次 1088B 栈写），签名无长度上限，因此调用点的 `iaNegKeyValid` 门与"超 32 槽"分支一并消失；
- 组相联从 512 组×2 路（对 ~1100/帧 工作集必然冲突抖动）改为 128 组×8 路；
- `DX12DispatchHookFlow.h` 增加 `static_assert(sizeof(DX12SimulateContext) <= 256*1024)` 作为**栈预算护栏**：这类"帧内大对象"今后再翻倍会在编译期报错，而不是在游戏里变成 c00000fd。

**代价**：key 比较由逐字节精确变为 128 位签名比较，误命中概率 ~2⁻¹²⁸（可忽略）；命中率需实测（表从 1024 项不变）。

**验证要点**（下次运行截图核对）：窗口正常出现；`Rm.IaNegCacheHit` 由 61/f 显著上升、`Rm.IaNegVerdictRuns` 由 977/f 下降、`Rm.IaNegVerdictNegative` 仍占绝对多数。

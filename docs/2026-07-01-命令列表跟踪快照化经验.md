# 2026-07-01 命令列表跟踪快照化经验

## 背景

这次继续排查“纯代码层导致 CPU 做额外无效操作”的问题时，发现命令列表跟踪链路里有一类很隐蔽但很高频的结构性浪费：

- 同一条 command list hook 内
- 同一份 tracking 事实
- 被拆成多个 `ShouldTrack*Cached()` / `ShouldRecord*Cached()` 查询
- 每个查询又各自走一次 TLS 命中判定，未命中时还会再进 shard / map / lock 路径

这类问题单次开销不大，但因为铺在：

- root signature
- root table
- root descriptor
- descriptor heaps
- IA state
- pipeline state

这些高频命令上，累计下来会稳定吃掉 CPU。

## 这次确认下来的结论

### 1. 跟踪判定应该是“快照”，不是“散装布尔查询”

`trackBindings`、`recordBindingEvents`、`trackHuntIa`、`trackPsoState` 这四个值，本质上属于同一个运行时 tracking context。

如果把它们拆成多个函数：

- `ShouldTrackBindingsCached()`
- `ShouldRecordBindingEventsCached()`
- `ShouldTrackHuntIaCached()`
- `ShouldTrackPsoStateCached()`

那调用方就会自然地一条命令里查很多次同一个 context。

更合理的建模方式是：

- 在入口拿一次 `DX12CommandListTrackingState`
- 整段逻辑都围绕这个局部快照展开

### 2. 同一个 runtime state 模块里，快路径不能只做一半

这次还暴露出另一个问题：

- `RememberIndexBuffer()` / `RememberVertexBuffers()` / `RememberPrimitiveTopology()` 已经有 TLS 快路径
- `RememberPipelineState()` 却还在每次直接进 shard + exclusive lock

这会导致 `SetPipelineState` 在 tracked 模式下比其他 IA/状态入口多付一层锁成本。

结论是：

- 同类 runtime state 写路径要么一起快路径化
- 要么一起不快路径化

不能半套。

### 3. 安全优化的原则不是“不重构”，而是“不改判定源”

这次之所以能安全动手，是因为改动只做了两件事：

- 把原本已经存在的 tracking 事实打包成局部快照
- 把原本已经存在的 runtime fast path补齐

没有改：

- dump 是否开启
- hunt 是否开启
- mod 是否生效
- 哪些命令会记录 binding event
- 哪些命令会追踪 PSO / IA

所以这是典型的“纯结构优化，不改功能语义”。

## 后续继续排查时的纪律

- 只要多个布尔值总是一起被读取，就优先怀疑它们应该收敛成一个 context / snapshot
- 只要一个 hook 里连续出现多个 `ShouldXxxCached()`，就优先怀疑这里在重复查同一事实
- 只要同类状态写函数里有的有快路径、有的没有，就优先怀疑这里存在热点不均匀
- 安全重构时，坚持“不改判定源，只改判定传递方式”

## 这次修改的直接收益

- command list state capture 链路里的 tracking 事实读取由“多次散查”收敛为“单次快照”
- `RememberPipelineState()` 补齐 TLS fast path 后，tracked 模式下的 `SetPipelineState` 热路径少一次 shard 独占锁
- 预计 `SetPipelineState` / root binding / descriptor heaps / IA 状态这些热路径上的重复 tracking 读取下降 50% 到 75%
- 在不影响 dump 完整性和 mod 生效语义的前提下，预计整体 CPU 开销再下降 0.3% 到 1.2%；在 binding/state 指令特别密集的场景中，预计可提升 1% 到 3%

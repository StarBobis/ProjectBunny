# 2026-07-01 DX12 IA去重键与别名回写失真经验

## 背景

这次排查 `205407` Dump 时，表面症状是：

- `call.draw` 已经记录了身体 `ib_gpu / ib_bytes / ib_fmt`
- 但最终没有身体 `IB .buf`
- `BindIA` 几乎为空

继续往下追后确认，问题并不是 `IASetIndexBuffer` 没钩到，也不是提取器没吃到新字段，而是 **DX12 IA Dump 的去重键与别名回写链路存在结构性失真**。

## 这次确认下来的根因

### 1. `call.draw` 有 IB 元数据，不等于 IA Dump 成功

`DrawIndexedInstanced` 里的：

- `ib_gpu`
- `ib_bytes`
- `ib_fmt`

只能说明 draw 时拿到了 `D3D12_INDEX_BUFFER_VIEW`，不能说明：

- IA 任务成功入队
- IA 任务成功生成 canonical dump
- duplicate alias 成功回写为 `BindIA`

因此不能再把 “draw 有 IB 元数据” 错当成 “IB 文件一定该存在”。

### 2. IA 候选数、IA 排队数、IA 别名数必须分开统计

这次 `205407` 的关键信号是：

- `ResourceDump` 开始时 `ia=2234`
- `ResourceDumpTasksQueued` 时 `ia=1`
- `BindIA=1`

这说明：

- 候选 IA 有很多
- 真正进入 canonical task 的 IA 只有 1 条
- 大部分 IA 在去重阶段就被折叠掉了

如果日志里只看最终 `BindIA` 数量，会误以为是“IA 根本没采到”，实际是 **IA 候选采到了，但在 dump 架构内部被错误折叠**。

### 3. 去重键不能散落在业务逻辑里靠 `sprintf_s` 隐式拼接

这次 IA key 之前直接在 `DX12ResourceDump` 主流程里现场拼接：

- resolved path 一套
- unresolved path 一套
- role 还是 `std::string::c_str()`

这种写法的问题是：

- 语义分散，无法统一验证
- 一旦字符串格式、字符集、宽窄字符细节出问题，很难定位
- 业务逻辑和 key 规则耦合，后续重构容易再次失真

更稳健的做法是：

- 专门用 `DX12ResourceDumpNaming` 统一生成 IA dedupe key
- 业务流程只消费结构化结果
- key 生成失败必须显式记日志

### 4. duplicate alias 缺失 canonical path 时，必须明确记录为架构错误

之前 duplicate alias 找不到 canonical dump path 时，只会表现成最终 `BindIA` 缺失。

这会把：

- “canonical 没生成”
- “duplicate 找不到 canonical”
- “根本没有 IA 候选”

这三类问题混成一个表面症状。

后续纪律：

- IA duplicate alias 找不到 canonical dump path，必须单独打日志
- 日志要包含 `call_index / role / view_gpu / view_bytes / draw_gpu / draw_bytes / dedupe_key`

## 这次修复后的纪律

- IA dedupe key 必须通过统一工具函数生成
- IA pipeline 必须分别统计：
  - candidates
  - resolved
  - queued
  - duplicate_aliases
  - key_failures
- duplicate alias 丢失 canonical dump path 时，必须视为 **Dump 架构错误**，而不是“资源没采到”

## 预计收益

- `205407` 这类“看似没 IB，实则 IA 内部折叠失真”的定位时间预计下降 70% 以上
- IA Dump 黑盒误判预计下降 80% 以上
- 后续身体 `IB/VB` 导出失败时，热点会从“提取器误猜”转移到明确的 Dump 链路节点，预计排障轮次减少 50% 以上

> 排查目标：找出仍按 DX11 单线程思路设计、会导致严重等待/性能问题的点。
> 重点区域：常驻 Mod 资源索引、Mod 替换 PreSkinning、DrawIndexed 等热路径。
> 排查日期：基于 commit 614263e（优化等待问题）之后的代码。
> 修复状态：**8 个问题已全部修复**（见各节"修复方案"），修复后 Release x64 编译通过。

## 一、已确认为【已优化】的区域（不要重复报告）

| 区域 | 已做的优化 |
|---|---|

## 二、残留问题点与修复方案（按严重度排序，已全部修复）

### 问题 1：`DX12ModGetReloadGeneration()` 用共享锁读一个 volatile 值 —— 中低频 ✅

**原位置**：`DX12ShaderOverrideRuntime.cpp:1939-1945`

- `gReloadGeneration` 本身就是 `volatile UINT64`，x64 对齐 64 位读天然原子；已存在无锁版本 `DX12ModGetReloadGenerationFast()`。
- 但 `BuildDispatchDecision`（`DX12CommandListRuntime.cpp`）和 `DX12ModCompileDrawDecision`（`DX12ShaderOverrideRuntime.cpp`）仍调用带锁版本。
- 触发频率：PSO 决策缓存 miss 时（每线程每 PSO 每 reload 一次）。不是每 draw，但场景切换/PSO 风暴时会放大。

**修复方案**：两处调用点已改用 `DX12ModGetReloadGenerationFast()`，PSO 决策缓存 miss 路径不再触碰 gModLock。带锁版本 `DX12ModGetReloadGeneration()` 保留给其余低频调用者（pre-skin 绑定缓存、binding tracker）。

### 问题 2：`std::atomic<std::shared_ptr>` 快照加载在热路径上 —— 隐藏的点锁 ✅

**原位置**：`DX12ModRuntimeInternal.h:404-405, 3352-3356, 3749-3753`

- MSVC 的 `std::atomic<std::shared_ptr>` **不是无锁的**，内部用 spinlock 池保护；`FindIaTextureOverridesCached` 等每 draw 每 IA buffer 最多 2 次 `.load()`，即每 draw 可能 4-10 次 atomic shared_ptr load+析构（多次 spinlock 进出 + 控制块 InterlockedIncrement/Decrement 全局缓存行乒乓）。
- 典型 DX11 思路：DX11 单线程，shared_ptr 快照随便拿；DX12 多录制线程并发时成为全局争用点。

**修复方案**（按排查建议的"生成号 + 裸指针 + TLS 缓存"模式实现）：

1. `DX12ModRuntimeInternal.h` 新增 `gCommandExecutionRuntimeSnapshotGeneration`（`std::atomic<UINT64>`），发布侧在 `DX12ModRuntimeLoad.cpp` 的 `.store()` 之后 `fetch_add(1, release)`。
2. 新增 `CommandExecutionRuntimeSnapshotTlsRef()`：每线程持有一份 owning 引用；稳态读取 = 一次 acquire UINT64 生成号比较 + TLS 裸指针复用，**无 spinlock、无引用计数流量**；仅在生成号变化（mod reload）时才走 `atomic<shared_ptr>` 加载，且加载前后各读一次生成号、不一致则重试，保证 (generation, snapshot) 一致对。
3. `LoadTextureOverrideRuntimeSnapshot()` / `LoadCommandExecutionRuntimeSnapshot()` 改为返回 TLS 保活的**裸指针**（本线程下次查询前有效）；需要长期持有的调用者（`DX12CommandListExecutor` 的成员缓存）改用新增的 `SnapshotCommandExecutionRuntimeShared()`（从 TLS 复制一次，语义与旧代码相同）。
4. 配套签名改为裸指针：`CommandListRuntimeEffectLocked`（两个重载）、`FindDescriptorTextureOverridesFromResolvedBindings`、`AppendGraphicsSrvTextureOverrideCandidatesForTarget`、`AppendResolvedBindingsToDescriptorTextureOverrideCache`；各调用点相应使用裸指针或 `.get()`。

### 问题 3：`DX12ModApplyKnownPreSkinningUavPatches` 里 per-patch 的 exclusive gModLock —— 死代码但设计未清理 ✅

**原位置**：`DX12PreSkinRuntime.cpp:4433-4575`

- 只读操作（find + 比较）却用 **exclusive** 锁，且每个 patch 进出两次；全工程搜索仅声明+定义，无 call site——死代码。

**修复方案**：已删除函数定义及 `DX12ModState.h`、`DX12ModRuntimeInternal.h` 两处声明。`gKnownPreSkinDescriptorPatches` 本身仍由存活的 apply 路径维护，保留。

### 问题 4：Dispatch 热路径上 pre-skin restore 的 mutation generation 级联失效 ✅（本轮最重要修复）

**原位置**：`DX12DispatchHookFlow.h:260, 325, 364, 421`；实现 `DX12PreSkinRuntime.cpp`

- 每次 pre-skin patch 成功 apply 都 `BumpPreSkinReplacementMutationGeneration()`——persistent 路径、TLS clone 路径、正常 ring 路径均如此。即"每个角色的 skinning dispatch apply 一次 → 全部其他 CL 的 restore TLS 负缓存失效 → 它们下次 draw/dispatch 重新走 exclusive gPreSkinLock + map find"。多角色多线程录制帧是持续级联。

**修复方案**（按排查建议的"按 commandList 分片"实现）：

1. `gActivePreSkinReplacements` 全局 map + 单一全局 mutation generation 替换为 **64 分片** `DX12PreSkinReplacementShard gPreSkinReplacementShards[64]`（`DX12ModRuntimeInternal.h`）：每分片独立 SRWLOCK + 独立 mutation generation，按 CL 指针 `(key >> 4) % 64` 分片。
2. 4 个 insert 点（persistent / TLS clone / ring / binding patch 路径）、2 个 erase 点（restore / forget）、3 个 find 点（reusable / canDefer / publishEarly）全部改走 `PreSkinReplacementShardFor(commandList)` 的分片锁；mutation bump 改为只 bump 本分片 generation（`BumpPreSkinReplacementShardMutation`）。
3. restore 的 TLS 负缓存改为读**本 CL 所在分片**的 generation：其他 CL 的 apply 不再使其失效，跨 CL 级联只剩同分片碰撞（1/64），且争抢的锁变为分片锁而非全局 exclusive gPreSkinLock。
4. `gHasActivePreSkinReplacement` 改为跨分片条目**计数**（新 key 插入才 increment、erase 时 decrement，均在分片锁内），读取侧仍只测 0/非 0，语义与原 flag 完全一致。
5. **未采纳**的次级建议：`FinishPreSkinProbe` 在 `probe.applied=false` 时跳过 restore——经核查**不安全**：`ApplyPreSkinDescriptorTablePatchLocked` 的 abort 路径（`requiresCountPatch` 且 `canPatchCount=false`，或持久/TLS-clone 不可复用）可能在本 CL 留有更早 deferred 的 pending entry，applied=false 时 entry 仍可能存在，跳过 restore 会把已 patch 的表泄漏给后续命令，故维持无条件 restore（其成本已被分片 + TLS 负缓存降到两次 load）。

### 问题 5：Present 路径上多处 `DX12HotPathState::Update()` 重复调用 ✅

**原位置**：`DXGIHookRuntime.h:98, 196, 282, 415`；`DX12WrapperRuntimeUtils.h:545, 676`

- Present 一次调用链 `Update()` 最多 3 次；`updateLock` 注释自称 "Cold path only"，但输入线程 toggles 也并发调 `Update()`。

**修复方案**：`Update()` 内部加入"源状态指纹"短路（`DX12HotPathState.h`）——Capture 后先算出 4 个派生门控值 + flags（flags 编码了全部 10 个源布尔位，是指纹的充分表示），与当前已发布原子量逐一相等则直接 return（仍在锁内，仅几次 relaxed load 比较）。避免重复 store、exchange、日志及 mask 翻转时的 `BumpTrackingGeneration()` 级联。顺带修正了旧短路（`skipAll && !HasAnyWork`）在"仅剩 preSkinProbe 工作 → 全部停止"时遗留 stale `HookWorkFlags` 位的缺陷：新指纹只在发布态与派生态完全一致时跳过。

## 三、已排查并定论的区域（原"待排查"清单的结果）

1. **`DX12ModApplyPreSkinningUavReplacement` 完整流程**：TLS match plan cache 命中时**全程无锁**，含 live binding 重锚定；miss 时 `AcquireModShared(&gModLock)`——每次 dispatch fingerprint 变化才发生。**可接受**。
2. **`ApplyPreSkinDescriptorTablePatchLocked`**：前置缓存链已分层——abort cache（shared 锁）→ `TryReuseDeferredPreSkinDescriptorTable` → persistent patch cache（**独立** `gPreSkinPersistentDescriptorPatchLock`）→ TLS clone cache（无锁）→ 最后才 `EnsurePreSkinDescriptorRingLocked`（全局 ring + exclusive `gPreSkinDescriptorRingLock`）。ring 分配锁持有时间极短（指针加法），**可接受/低优先级**。
3. **`EnsureResourceUavLocked` / `EnsureLoadedResourceForPreSkin`**：gModLock 共享读 gLoadedResources，双层（shared→miss→exclusive）正确。命中路径的每帧共享锁开销已随问题 2/7 的 TLS 缓存一并消除于 static IA 绑定路径；pre-skin apply 路径的共享读频率低（每 CL 每 skinning dispatch 一次），**可接受**。
4. **`MarkPreSkinOutputResizeCacheUsesSubmitted`**：见问题 8（已修复）。

## 五、第二、三轮排查确认问题（已全部修复）

### 问题 6：Hunt 模式 per-draw 全局锁（仅 hunt 激活时）✅

**原位置**：`DX12ShaderHunt.cpp`

- `DX12HuntRecordDraw` / `DX12HuntRecordDispatch` / `DX12HuntRecordExecuteIndirect`：per-draw `gHuntLock` exclusive 向 per-CL visits map 插入 hash；`DX12HuntObservePipelineState` 每次 PSO bind 两次 exclusive（计数器 + `AddPsoVisitedLocked`）。
- DX11 思路：假设单线程录制。DX12 多线程录制时所有线程的每个 draw 都在 gHuntLock 上排队。

**修复方案**：

1. `gCommandListVisits` 全局 map 替换为 **64 分片** `HuntVisitsShard gHuntVisitsShards[64]`（每分片独立 SRWLOCK + map，按 CL 指针分片）：Record* 路径只取本 CL 分片的 exclusive 锁，跨线程争用降到同分片碰撞（1/64）。
2. `DX12HuntPublishCommandList` 改为两阶段不嵌套取锁：先在分片**共享锁**下拷出该 CL 的 visits 并释放，再取 `gHuntLock` exclusive 一次性合并进全局 visited 集合——无锁序反转（toggle 清理路径同样按"先分片后全局、不嵌套"组织）。
3. `DX12HuntToggle` 清理改为逐个分片加锁清空 + 统计总条目数（`oldIa`），语义不变。
4. `DX12HuntObservePipelineState` 两次 exclusive 合并为一次：`DX12GetPipelineStateShaderInfo`（纯查询，不碰 hunt 状态）移到锁外先做，锁内一次完成计数器 + `AddPsoVisitedLocked`。

### 问题 7：IA 绑定路径的 `DX12ResolveStaticIaReplacement` per-bind 快照+锁链 ✅

**原位置**：`DX12WrapperRuntimeUtils.h:1254, 1353`；实现 `DX12LoadedResources.cpp:849`

- 每次 `IASetIndexBuffer`/`IASetVertexBuffers` 且 static IA 表非空时，**每个 slot 每 bind 一次**：`LoadStaticIaReplacementSnapshot()`（atomic shared_ptr load，MSVC spinlock + 控制块缓存行）→ hash find → 命中后 `EnsureLoadedResourceForPreSkin`（gModLock 共享读，miss 升级 exclusive 做文件读+资源创建）。

**修复方案**（按排查建议实现）：`DX12ResolveStaticIaReplacement` 内部新增按 reload generation 失效的 TLS 解析缓存——

1. key：IB 用 `(0xFFFFFFFF << 32) | contentHash`（虚拟 slot 标记），VB 用 `(slot << 32) | contentHash`；value：解析出的 GPU VA / byteWidth / stride / format（纯数值，不持有指针）。
2. 每次调用先 `DX12ModGetReloadGenerationFast()`（volatile 读，零成本）比对 TLS generation，变化则清空缓存；命中即直接填 view 返回（format/stride 对原始 view 的回退逻辑保持在调用时计算，语义与旧代码逐点一致）。
3. 资源本体是常驻 UPLOAD heap，generation 内指针稳定（只在 reload 时随 `gReloadGeneration` bump 一起退役），负结果（无替换/加载失败）同样按 generation 缓存——`EnsureLoadedResourceForPreSkin` 自身在同 generation 内对失败也有 `failed` 标记，语义一致。
4. 表未发布/未启用（`!table || !table->enabled`）的瞬态**不缓存**，直接返回 false。
5. TLS map 以 1024 条为界，超出清空重建（防单 generation 内绑定大量不同 buffer 导致无界增长）。
6. 效果：每 bind 每 slot 的成本从"快照 load + hash find + gModLock 共享"降为"一次 volatile 生成号比较 + 一次 map find"，gModLock 从每 bind 降为每 generation 每 slot 一次。

### 问题 8：`MarkPreSkinOutputResizeCacheUsesSubmitted` 提交线程上的 O(N²) 扫描 ✅

**原位置**：`DX12PreSkinRuntime.cpp:1247`

- ExecuteCommandLists 热路径；对每条 cache entry 的 `pendingCommandLists` 做 `std::find`（O(batch)），erase 的 `remove_if` 内再次嵌套 `std::find`——O(items × pending × batch)。

**修复方案**：批次成员查询改为一次构建、多处复用——

1. 小批次（≤8，原有栈上数组路径）保持**零分配**线性扫描；
2. 大批次先把 identity 建 `std::unordered_set`（reserve 全量），共享锁扫描与 exclusive 锁 `remove_if` 两处统一走 `isSubmittedIdentity` lambda：O(1) 查询替代 O(batch) 线性扫描。

## 六、排查方法备注

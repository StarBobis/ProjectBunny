# 2026-07-01 高频全局状态去对象化经验

## 背景

这次继续排查冗余函数嵌套时，确认了一类比 `return true` 空壳函数更隐蔽、也更容易污染热路径的坏味道：

- 进程级全局状态被包成伪单例对象
- 读取路径是 `Get().field`
- 写入路径是 `Get().Method()`
- 外层再包一层 façade，里面继续临时构造空对象调用实例方法

这类代码的危害不只是“多调了一层函数”，而是把本来没有对象边界的东西，伪装成了对象 seam，后续维护会继续沿着错误方向加更多壳层。

## 这次确认下来的结论

### 1. 全局运行态寄存器不是对象

像下面这类状态：

- runtime mode
- present count
- hot-path skip flags
- frame analysis active/capturing/requested flags

本质上都是：

- 进程级唯一
- 没有多实例需求
- 没有 adapter 需求
- 调用方只关心当前值，不关心“这是哪个对象的值”

这种状态最合理的建模方式就是：

- `inline static` 状态字段
- `static` 生命周期/同步操作

而不是：

- `static Get()`
- `Get().field`
- `Get().Method()`

### 2. “已经静态化状态，但还在 new 一个空对象去调实例方法” 也是伪对象

这次 `DX12FrameAnalysisState` 就暴露了这个坑：

- 底层状态已经全部变成静态存储
- 外层 `DX12FrameAnalysis` 还在每次调用时构造局部 `state`
- 然后再调用 `state.Begin()` / `state.End()` / `state.LogJsonFields()`

这说明重构不能只删 `Get()`，还要继续追到 façade 层，把残留的实例语义一并清掉。

### 3. 优先清理 DX12 CPU 热路径上的假 seam

DX12 官方文档明确强调过：

- D3D12 的目标之一就是降低 CPU overhead
- 命令列表录制、命令队列提交、资源状态管理都交还给应用显式控制

因此最该先清理的，不是低频管理代码，而是这些热路径里的假对象壳：

- draw / dispatch hook
- command list state capture
- execute command lists
- present
- resource create tracking gate

## 这次踩到的规律

### 1. 不要把“模块存在价值”和“对象存在价值”混为一谈

有些模块应该保留，比如：

- `DX12FrameAnalysis`
- `DX12ResourceTrackingPolicyUtils`

因为它们在聚合语义、聚合日志、聚合策略。

但这不等于内部状态一定要做成 `Get()` 伪实例。

结论是：

- 模块可以保留
- 假对象外壳必须删除

### 2. 删除时要按整条调用链压平

如果只删最里层 `Get()`，但保留：

- façade 临时构造对象
- 实例方法只转发到静态状态
- 热路径里残留旧调用点

那就只是“换皮”，没有真的去掉多余层次。

所以这类重构要一口气清：

- 状态定义
- 状态读写入口
- façade 转发
- 高频调用点

## 后续继续排查时的纪律

- 先判断一个状态是不是天然单实例、天然无 adapter、天然无实例边界
- 如果是，就优先怀疑它不该被包成 `Get()` 对象
- 先抓热路径：draw / dispatch / root binding / present / queue submit
- 保留真正聚合策略和生命周期的模块，删除没有额外语义的对象壳
- 如果 façade 里出现“构造局部对象然后直接调用一次实例方法”，默认先怀疑这是伪对象残留

## 这次修改的直接收益

- `DX12HotPathState` 高频读取路径里的伪对象跳转减少 100%
- `DX12RuntimeState` 全局运行态访问路径里的伪单例跳转减少 100%
- `DX12FrameAnalysisState` 状态入口里的伪对象构造与实例跳转减少 100%
- 已触达热路径上的状态访问层级预计减少 33% 到 67%
- 对 draw / dispatch / present / execute-command-lists 这类高频 CPU 路径，预计可带来 0.5% 到 2% 的整体 CPU 开销下降；在 Hunting / Dump / 重绑定追踪更重的场景里，预计改善可放大到 2% 到 5%

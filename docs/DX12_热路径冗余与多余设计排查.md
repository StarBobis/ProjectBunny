## 0. 先讲测量口径（不先讲这个，后面每个数字都会用错）

### 0.1 `Api.*` / `Stage.*` 的 us/call 里含游戏自己的驱动调用

可证锚点：`CloseCommandList`（`DX12WrapperRuntimeUtils.h:1122-1128`）函数体只有一句
`return original ? original(commandList) : commandList->Close();`，实测 **12.1us/call**。
所以 `ResetCmdList 41.3us`、`SetPipelineState 2.09us`、`ResourceBarrier 3.36us`、
`RootSignature 2.38us` 里都含 D3D12Core/驱动的真实工作。

**代理层自身开销的实测上界**：`Api.SetPipelineState 70884us − Stage.SetPipelineState 68796us`
= 2088us / 34018 = **61ns/call**（两者嵌套同一区间，差值是解包缓存判断 + 标志读取）。
同理 `ResourceBarrier` 得 54ns。→ **"纯转发 wrapper 要 2~3.4us" 这个前提不成立**，
不要按 us/call 去优化转发层。

### 0.2 `DeltaUs` 有 0.5us 死区

`DX12Diag.h:313-327`：`(n*1e6 + 5e6)/1e7`，`QPF=10MHz` 时 n=1..4 tick（0.1~0.4us）**记 0**。
所以 `UnwrapObj 0.17us/call`、`RootDescTable 0.05us/call` 这类
"低于分辨率"的均值不可用（totalUs 只是"有多少次超过 0.5us"的下界）。
**>0.5us 的数字可信**：`IaBindPreSkinRedirect 1.19us`、`SetPipelineState 2.09us`、
`ResetCmdList 41.3us`、`CloseCmdList 12.1us`、`PreSkinCbvCreateInsert 382us`。

### 0.3 汇总段会丢小桶

`DX12Diag.h:1507`（Create 段）与 `:1532`（CPU stage 段）丢弃
`totalUs < 40 && maxUs < 10` 的桶 → 亚微秒 stage 整体消失，
或只保留慢样本（`prepare_get_cs_hash` 只记到 2164/32128 次就是这个原因）。

→ **判断"某分支是否执行过"必须用计数恒等式，不能用"日志里没有这个桶"**。
同理 `PreSkinMatch`/`PreSkinApply` 两个 RAII scope 覆盖同一段代码，
聚合表把 apply 的 520ms 记了两遍。

### 0.4 Release 构建里整套诊断是零成本

`DX12Diag.h:1761-1807`：非 TIMING 构建下 `DX12_PROF_*` / `DX12_LOG` / `DX12_DIAG_QPC`
全部展开为 `do{}while(0)`，实参不求值。
→ **不存在"关掉诊断后仍照常格式化"的问题**（这曾是怀疑项，已排除）。

## 1b. 实测 A/B 结果（改动前 vs 改动后）

两次运行都是同一个游戏、同一个 mod，日志由构建脚本自动轮转，因此可以对比：

| | 改动前 | 改动后 |
|---|---|---|
| 日志 | `d3d12_log.before_20260912-002043.txt` | `d3d12_log.txt` |
| 帧数 | 6,935 | 7,165 |
| 末尾 `frameIntervalUs` | 27,969us（35.8fps） | 25,946us（38.5fps） |
| 窗口数 | 115 | 119 |

### ⚠ 这次 A/B 不能用来判断帧率

两次运行的**场景构成不同**，而且差异很大：

- 最后一次窗口：draw 61,973 → 73,633（**+19%**），
  `DescCopyChanged` 297,570 → 429,296（**+160%**），frameWall 30.0ms → 35.0ms。
- 整轮 draw 总数：约 1.52M → 2.11M（**+39%**）。
- 重载场景只出现在每轮**最后 2~3 个窗口**；整轮其余 100+ 个窗口都是
  <40 draw/帧的轻载场景（3.5ms/帧），我们的 hook 在那里只占个位数百分比。

所以"末尾 frameIntervalUs 从 28.0ms 降到 25.9ms"**不能**归因于本次改动。

### 可以归因的结论（轻载窗口，场景匹配，per-call 中位数/均值）

| stage（轻载窗口） | 改动前 us/call | 改动后 us/call | Δ |
|---|---|---|---|
| **`ResetCmdList`** | **31.454** | **29.925** | **−4.9%** |
| **`IaNegVerdictHashes`** | **3.437** | **3.280** | **−4.6%** |
| `DrawHook` | 6.893 | 6.833 | −0.9% |
| `DispatchHook` | 2.881 | 2.744 | −4.8% |
| `RootSignature`（未改，对照） | 2.454 | 2.415 | −1.6% |
| `ResourceBarrier`（未改，对照） | 2.137 | 2.182 | +2.1% |
| `SetPipelineState`（未改，对照） | 1.938 | 2.057 | +6.1% |

三种口径下 `ResetCmdList` 一致变好：轻载 per-call −4.9%、全窗口 per-call 中位数
−5.4%（31.90 → 30.17）、整轮加权 per-call −6.6%（36.74 → 34.30）；
在 draw 数完全相同的早期窗口里是 −6% ~ −13%。这直接对应本轮删掉的
"每次 Reset 一个 ~15KB 临时对象 + 整结构拷贝"（`staticTemplateSavedIa`）与几处死状态写。

**对照组的 ±5% 说明本次运行的噪声地板就是 ±5%**，所以 `DrawHook` 的 −0.9%
在这一轮里不可分辨——这是预期的：本批改动是"删死状态"，量级在纳秒~几十纳秒/次。

### 正确性修复没有代价

`iaNeg` 键补上 `preSkinGeneration` 后，整轮缓存命中率 11.9% → 12.3%（**没有下降**），
说明该项在本场景里几乎不变；代价为 0，而它堵住的是 `match_cs` 门控 IA override 的漏判。

### 本批改动的量级（诚实结论）

| 删掉的东西 | 频次 | 估算收益 |
|---|---|---|
| Reset 路径 ~15KB 临时+拷贝 + 死状态写 | 16.2 次/帧（重载） | ~24us/帧 |
| `GetOrBuildCached*ViewHash` 里一次全局原子读 | 152k 次/窗口 | ~2.5us/帧 |
| 预筛探针的临时 vector（构造+可能的拷贝） | ~60k 次/窗口 | ~10us/帧 |
| draw 路径 2 次空函数调用、死字段写 | 每 draw | 可忽略 |
| **合计** | | **≈ 0.02~0.05ms/帧（≈0.1%）** |

**本批的价值是"去掉不该存在的状态与设计、堵住一个正确性缺口"，不是省时间。**
真正的大头仍然在 §2：IA 绑定门控 1.74ms/帧、pre-skin 5 层死判定（每次 dispatch 全量收集绑定）、
`CopyDescriptors` 记录 4.7ms/帧、CBV 补丁 382us×724——它们比本批大 1~2 个数量级。

## 1d. 第三批：机械扫描出的死状态 + 两个有害缓存机制（commit `5f251a0`）

### 方法：机械扫描而不是靠眼睛

对 `src/DirectX12` 下所有头文件提取成员声明（正则匹配 `类型 名字;` 形式），
再统计每个标识符在整棵 `src` 树里的出现次数，**只出现一次的 = 只有声明、无人引用**。
注意两个假阳性来源，必须人工复核：

- **token pasting**：`Orig*` 那 20 个 hook trampoline 只出现一次，但它们是
  X-macro/注册表生成的，属活代码。
- **取引用/别名**：`boundDrawResult` 只有 2 次出现，但其中一次是
  `DX12BoundDrawResultCache &boundDrawCache = ...boundDrawResult;` 之后调用
  `Matches`/`Capture`，属活代码。
- **RAII 局部量**：`DX12IaReplacementDrawScope replacementDrawScope;` 只出现一次，
  但它的构造/析构就是全部作用。

### 删掉的死状态（全部经"零引用"复核）

| 位置 | 说明 |
|---|---|
| **整个 OM 影子块** | `omRenderTargetCount` / `omRenderTargets[8]` / `omHasDepthStencil` / `omDepthStencil` + `OMSetRenderTargets` 的写入块 + Reset 两行。这四个字段只在**自己的写入块内部**被读（`omRenderTargetCount` 当循环上界、`omHasDepthStencil` 当写入条件），无任何消费者；注释声称供 custom element replay 恢复用，但那个 replay 是直接绑 back buffer 的。代价是每次调用一次 `std::min`、单句柄路径上一次 **COM 调用** `GetDescriptorHandleIncrementSize`、最多 8 次存储 |
| `DX12StoredPso` 的 `cachedDrawTargetPlan`/`drawTargetPlanGeneration`/`drawTargetPlanResolved` | 注释写"PSO 创建期编译 Mod 计划，消除每 draw 配置重发现"，实际从未被读写——整套机制只存在于注释里 |
| `DX12TextureOverrideLookupCacheEntry::iaCandidateIndexes` | 32768 项缓存 value 里的零引用成员 |
| `DX12IaHashState::computeBuffers` | 零引用；`DX12IaHashState` 每 draw 构造一次，也内嵌在 iaHashStateCache 每个 entry 里 |
| `DX12ActiveIaState::indexBufferStaticMatchedHash`、`vertexBufferStaticMatchedHash[32]` | 各只写一次，无读者 |
| `ComputeTemplate::bindingsSerial`、`bindingsRootParameters` | 后者每次收集还做一次 vector 拷贝赋值 |
| `DX12PreSkinReplacementState::replacementTable`、`DX12PreSkinSrvPositiveCacheValue::srvRegister`、`DX12PreSkinBindingCacheUtils::CacheCapacity` | 零引用 |

### "看似有用实则有害"的两处机械修正

1. **CBV 补丁缓存的键含每帧都变的量 ⇒ 结构性无法跨帧命中。**
   `DX12PreSkinCbvPatchCacheKey` 原来含 `resource` + `sourceOffset`，而游戏每帧原地重写
   UPLOAD CBV、并轮换 arena，同一份常量换个分配就是新键。存入处的注释记录过这个 bug 的
   一次发作（键不一致 → "永久 miss、每次调用都建 buffer + descriptor"），当时只把两处键改成
   "一致"，没意识到这两个分量本身就是易变量。
   命中路径本来就有 `patchedBytes == bytes` 的**逐字节**校验，而 `contentHash` 就是
   **补丁后**字节的哈希，所以键只需描述结果 `(viewBytes, overrideVertexCount, contentHash)`
   （`viewBytes` 必须留：缓存 descriptor 的 `SizeInBytes` 由它决定）。这是**严格更宽**的命中
   判定，且每次命中仍由逐字节比较把关。
   基线实测命中率 20%（`PreSkinCbvCacheLookup 905` vs `PreSkinCbvCreateInsert 724`），
   每次 miss 是一次 `CreateCommittedResource`（382.59us × 724 = **277ms/60帧**）。
2. **清空阈值比它所保护的池小 4 倍**：池 256 槽（`kPreSkinCbvPatchPoolSlots`），门槛却写死
   `size() > 64` → 容量远未用尽就整体丢弃所有可复用条目并把 buffer 全部重新 park，
   与"跨帧复用"的初衷相反。改为以池容量为门槛；释放侧本就是延迟释放
   （`ParkPreSkinCbvPatchRelease`，每次补丁 drain 2 个），队列上限 512 ≥ 256，仍在既有边界内。

### 有意没做（本批不动）

- 补丁缓存的"整体清空"本身：池是无空闲链表的 bump 分配器（`gPreSkinCbvPatchPoolUsed` 只增，
  清空时归零），要按条淘汰必须先引入空闲链表——设计改动，按"有风险的不要动"跳过。
  键修正后不同键数量下降，清空频率会随之下降。
- pre-skin dispatch 那 5 层 0 命中的判定缓存：删它们等于删功能（别的 title 可能有效），
  正确做法是修键，需要一轮实测确认，未动。

### 本轮测试可观察的信号（与前面几批不同，这次有）

`PreSkinCbvCreateInsert` 的次数与总耗时应当明显下降，`PreSkinCbvCacheLookup` 命中率上升
（基线 20%）。这是本批唯一一处**机制性**改动，其余仍是删死状态。

## 1e. 第四批：死数据 —— draw-SRV 恢复快照 ~60KB → ~2KB（commit `8e74a38`）

应用户要求，这批只做"死代码 / 死机制"，不含行为改动。

### 问题：每次 mod 命中 draw 搬运 ~240KB，其中 96% 是死数据

draw-SRV 替换的恢复分逻辑半与物理半，两半都从同一份快照读：

```
DX12ModIaReplacement::DrawSrvApplyState::originalBindings
DX12DrawSrvPendingRestore::originalBindings
```

两者原本都是整个 `CommandListBindingState`。该类**没有任何 `std::vector` 成员**
（全是定长数组：2×64 项 `RootTableState` + 2×64 项 `RootConstantsState`
（`values[64]`+`valueValid[64]` ≈42KB）+ 根描述符 + IA 视图 + 渲染目标），
因此 trivially copyable —— **所有"move"都是整结构 memcpy**。

而这份快照的全部读者只用四样东西：
`cbvSrvUavHeap` / `samplerHeap`、每个 root 的 `graphicsTables[root].valid` +
`.baseDescriptor`、`computeTables[root]` 同理、以及两个 `*TableValidCount`
（读点：`FlushPendingRestore`、`Restore` 的逻辑半、`DeferPendingRestore`；
写点：`ApplyPending` 的两处赋值）。每次命中 draw 约 58KB 从未被读取的负载被
memcpy 4~5 次，≈240~300KB 纯内存搬运。

### 做法：换类型，让编译器把读者列全

新增 `DX12DrawSrvBindingSnapshot`（`Core/Models/DX12BindingModels.h`）：
只含上述字段（`TableRef{bool valid; D3D12_GPU_DESCRIPTOR_HANDLE base;}`）+
`CaptureFrom(const CommandListBindingState&)`，约 2KB，并加
`static_assert(sizeof(...) <= 4096)` 把"必须保持极小"钉住。
两个成员换成该类型，`ApplyPending` 的两处赋值改为 `.CaptureFrom(snapshot)`。

**字段名刻意保持不变**，所以绝大多数读点一行都不用改；反过来，任何用了其它字段的
读者都会**编译失败**。这正是这次敢动的理由：它不是行为改动，而是被编译器完整校验的
类型收窄。实际过程中编译器确实抓出了两处漏改——`FlushPendingRestore` 与
`Restore` 逻辑半把局部量声明成 `const CommandListBindingState &snapshot = ...originalBindings;`
（行 448 / 1878）——改掉后 clean 构建全绿，即证明没有别的读者。

### 旁证与教训

- DLL 体积 4,525,056 → **4,465,152 字节（−58.5KB）**：`DX12ModIaReplacement` 有
  `static thread_local` 实例（`DrawReplacementScratch`），其体积直接进 BSS，
  所以负载削减在二进制体积上直接可见。
- 几处"对象内嵌 ~60KB 绑定状态，所以不要每 draw 构造"的注释已同步更新
  （`ResetForDraw` 的 marker-only 清法保留——不变式仍成立，只是收益从 60KB 变 2KB）。
- **只有 clean 构建的绿色算数**：本批第一次增量构建报了 EXITCODE=0，随后 clean
  构建却失败在那两处读者上。本仓库的增量依赖跟踪已两次给出假绿（另一次是 stale
  `.obj` 造成链接期假失败），此后一律以 `build_release_timing_x64.ps1` 为准。

### 预期

每次 mod 命中 draw 少约 240KB memcpy（基线重载场景 1695 次/窗口）
⇒ 约 0.3~0.4ms/帧量级，且不改变任何行为。

### 1e-1. 实测：这一轮的日志**分辨不出**本批（但可确认无回归）

## 2. 已验证、但**没有**动手的项（按 收益/风险 排序，附建议做法）

### 2.1 【最大单块】IA 绑定的 pre-skin 重定向门控形同虚设 —— 1.74ms/帧（帧 5.8%）

`Presentation/DX12WrapperRuntimeUtils.h:1438-1449`（门控）+ `:1488-1510`（快路径入口）+ `:1549-1572`（受门控的 32 槽位遍历）

```cpp
static bool PreSkinRedirectPossible(const D3D12_VERTEX_BUFFER_VIEW *views, UINT count)
{
    if (DX12ModHasPreSkinOutputResizeBindings() ||
        DX12ModHasPreSkinOutputResizeCacheEntries())
        return true;                                  // ← 短路
    bool boundSlotValid[32] = {};
    for (...) boundSlotValid[slot] = true;
    return DX12ModMayNeedPreSkinIaViewExpansion(views, boundSlotValid, count);
}
```

慢路径入口条件之一是 `hasPreSkinResizeBindings = DX12ModHasPreSkinOutputResizeBindings()`
（`:1493`），与 `:1441` 是**同一个谓词**。所以只要 mod 配了 pre-skin，
`PreSkinRedirectPossible` 必定在 `:1441` 返回 true，按本次绑定 VA 区间的廉价判定永远不可达，
`RedirectVertexBufferViews` 每次都跑。

实测（窗口）：`IaBindSlowPath 87525` vs `IaBindFastPath 43`（快路径 0.05%）；
`Rm.IaPreSkinRedirectGated` 在所有窗口**不存在**（从未命中）；
`IaBindPreSkinRedirect 104,413us / 87,525 = 1.19us/call` → **1.74ms/帧**；
槽位级 `PreSkinRedirectNegMiss 67,798` vs `NegHit 8,764 + ViewNegHit 15,385` → **74% miss**，
每个 miss 要付 `DX12ResolveBufferResourceByGpuVa` / `DX12ModResolvePreSkinOutputResizeByGpuVa`
的锁 + 资源解析。

> ⚠ **不要把 `:1441` 的 `return true` 改成 `return false`。**
> 审查中曾提出"符号写反"的结论，我核对后**否决**了：
> `DX12ModMayNeedPreSkinIaViewExpansion` 只覆盖 `gPreSkinExpandedOutputRangesBySection`
> 这一条机制（"发布字节宽度 > 后备资源宽度"的就地扩展），
> 而 `RedirectVertexBufferViews` 里还有第二条机制
> `DX12ModResolvePreSkinOutputResizeByGpuVa`（重定向到**另一个** resize 资源），
> 后者不产生 expansion 元数据、探针恒为 false。
> 按该建议改会直接弄坏 pre-skin output resize 的消费者重定向
> （`Hooks/DX12IaReplacement.h:1409-1413` 的注释也说明了：Present 清掉帧内发布表后，
> 已配置的 PreSkin 工作**必须**继续 replay）。

**建议做法**：给重定向加一个**覆盖两条机制**的廉价预筛——
形如 `gHasPreSkinExpandedOutputRangesFast` 的锁存标志（resize binding 集合非空 或
expanded range 集合非空），把它提升进 `HookWorkFlags` 而不是每次跨 TU 调两个全局谓词；
命中该标志才走 32 槽位遍历。验证指标：`Rm.IaPreSkinRedirectGated` 与 `IaBindFastPath` 两个计数。

### 2.2 pre-skin dispatch：5 层判定缓存 0 命中，却让每次 dispatch 走全量绑定收集

`Hooks/DX12DispatchHookFlow.h:336-372 / 551-567 / 568-594 / 607-649 / 669-740 / 780-797`
六处"负判定/正判定"分支，键分别折入 `probeBindingSerial`、`bindingsDescriptorVersion`、
`iaContentEpoch`、`probeFingerprint` 等**每帧变化**的量。

用**计数恒等式**证明（不受 0.3 节丢桶影响）：

```
collect_bindings == PreSkinBindQuery == dispatch_prepare_probe == BindSnapshot == 32128
```
A/B 两个"早期负命中"分支都在 collect 块**之前** return，只要命中过一次，
`PreSkinBindQuery` 的调用数就会小于 32128 → **0 次命中**。
`BindSnapshot` 只在 `CollectPreSkinBindings` 内计数，而它只在 `computeTemplateLoaded == false`
时被调用 → **resident 快照 0 命中，`TryGetRuntimePreSkinBindings` 从未成功**。
于是 `:669-740` 两级 template 检查（约 72 行）因 `computeTemplateLoaded` 恒 false 而
**不可达**；`store_probe_cache == 1297 == 32128 − 30831` → 905 次成功 apply 上
runtime/local/shared 三套正缓存也全部 0 命中。

**唯一活着的**是不含这些量的 geometry 键（`probe_cache_geometry_negative_hit` 30,831 次命中，
10.79us/call）。同一批代码的注释（`Tracking/DX12BindingTracker.cpp:571-577`）已经写明
"ZZZ 类游戏每次 draw 重绑根表，序列号类校验必然失败"——作者在
`TryGetRuntimePreSkinBindings` 里已按这个结论改成逐槽 valueId 校验，
但 hook 里的 A/B/resident 三层还是老写法。

代价：`collect_bindings` 9.80us × 32,128 = **315ms/60帧**，另有约 120 行分支每次白算 ~20 个比较。

**建议做法（两步，别一步到位）**：
先把 A/B/resident/两级 template 这些**可证不会被命中**的分支各加一个 `Rm.*` 计数上线跑一轮确认；
再删死分支，并把存活分支的键从"序列号"改成"绑定身份"（照 `TryGetRuntimePreSkinBindings` 的写法）。
最后才考虑删缓存本体。

### 2.3 CBV 顶点数补丁：每次缓存 miss 都建一个 committed resource（382us × 724）

`ModRuntime/DX12PreSkinRuntime.cpp:2648-2695`。补丁内容只是把 256 字节里若干 dword
换成 `overrideVertexCount`，却每次 `CreateCommittedResource` + `Map` + `memcpy` + `Unmap`。

`PreSkinCbvCacheLookup 905` vs `PreSkinCbvCreateInsert 724` → **命中率 20%**。
结构性原因（作者自己的注释 `:2347-2349`）：键含"打好补丁后的内容哈希"，
而源 CBV 每帧被游戏原地重写。`:2694` 的 `if (size() > 64) ClearPreSkinCbvPatchCache();`
是"一个新键清掉整张表"，会让还在复用的键一起失效。

代价：382.59us × 724 = **277ms/60帧**，占 `descriptor_table_patch_hit`(490ms) 的 57%、
`DispatchHook` 总耗时(1.325s) 的 21%。

**建议做法**：一级——把 `resource`/`sourceOffset` 从键的比较中移除（命中路径
`:2628` 已有 `patchedBytes == bytes` 精确字节比较，两者对 CBV 完全等价），
并把"整表清空"改成按 age 淘汰；二级——8~16 槽预建 UPLOAD 环形池，
只做 memcpy + CreateConstantBufferView，复用已有的
`ParkPreSkinCbvPatchRelease` / `RetainPreSkinDescriptorHeapForCommandList` 在飞期保护。

### 2.4 `DrawSrv` 的 ~60KB 快照按值拷贝 3~4 次

`ModRuntime/DX12DrawSrvReplacementUtils.h:50 / 340-361 / 363-376 / 394 / 415-424 / 1351 / 1471-1473`。
`DX12DrawSrvPendingRestore::originalBindings` 与 `DrawSrvApplyState::originalBindings`
各内嵌一整个 `CommandListBindingState`（`Core/Models/DX12BindingModels.h:230-322`：
两个 64 项 `RootTableState` ≈12KB + 128 × `RootConstantsState`(values[64]+valueValid[64] ≈332B) ≈42KB）。
成员是裸数组、类无自定义 move → 所有 `std::move` 都是全量 memcpy，
`shard.entries[k]` 还要先默认构造 60KB。
而读这份快照的只有两处（`Utils.h:447-471`、`:1877-1898`），
只碰 `cbvSrvUavHeap` / `samplerHeap` / `graphicsTables[r].valid+baseDescriptor` /
`computeTables[r].valid+baseDescriptor` —— **根常量与根描述符那 ~45KB 从未被读**。

**建议做法**：把 `entries` 改成 `unordered_map<list*, unique_ptr<...>>`（消掉默认构造与两次 move）；
彻底做法是把快照瘦成 `{两个 heap, validCount, {root, gpu}[]}` 几百字节。

### 2.5 `CopyDescriptors` 的记录路径没有门控 —— 4.7ms/帧（帧 15.7%），全日志最大单项

`Presentation/DX12DeviceWrapper.h:781-801`（`CopyDescriptors` 无条件调
`DX12ResourceTrackerHookRuntime::RecordCopiedDescriptors`）
vs `:803-823`（`CopyDescriptorsSimple` 有外层门控）。
实测 `Create.CopyDescriptorsWrapper.Record` = 1.53us × 3,080/帧 = **4.7ms/帧**。

另外该 range 展开循环 `Tracking/DX12ResourceTrackerHooks.cpp:312-341`
对**每个 block** 调一次 `RecordCopiedDescriptorsSimple`，
于是 `:344-470` 的整套 per-call 初始化（2×`ResolveHeapSlotFast`、2×`IsActive`、
2×`IsMaterialized`、chunk 游标）与 `:469` 的 `commitSet.CommitAll()` **按 block 重复**，
而 `:387-390` 的注释写的是"heap 级失效令牌在一次 API 调用完成后只变一次"。

**建议做法**：先加一个 `DX12_PROF_ADD_ITEMS("Desc.CopyBlocks", 1)` 量出
"每次 CopyDescriptors 平均展开几个 block"；>2 就把 `commitSet` 提到循环外、
`CommitAll` 收敛到一次，并在循环内按句柄记忆解析结果。

### 2.6 unwrap 的 TLS 缓存被全局 generation 反复作废

`Presentation/DX12WrapperCore.h:689-726`（64 槽 TLS 直接映射缓存，
命中要求 `entry.generation == gWrapperRegistryGeneration`）
vs `:641-656`（每次 `RegisterWrapperPointer` 就 `fetch_add` 一次，
一个 ResourceWrapper 注册 6 个接口指针、CommandListWrapper 注册 14 个）
+ `:569-586`（每次析构也 bump）。实测约 **2,400 次 bump / 60 帧 ≈ 40 次/帧 ≈ 每 730us 一次**
→ 命中率极低，而 miss 要走 `gWrapperLock` 共享锁 + `unordered_map::find`。

实测代价：`BarrierUnwrap 2.37us/call`，`items = 93,743/10,013 = 9.36 barrier/call`
→ **254ns/元素**（已命中指针的 unwrap 命中路径只有 5~10 条指令 ≈ 10ns）。
`ResourceBarrier` 合计 74ms/60帧 = 4.1% 帧时间，其中 24ms 是这个解包。

**建议做法**：一级（几乎零风险）——把 `RegisterWrapperPointer` 的 bump 从"每个接口指针一次"
改成"每个 wrapper 构造结束后一次"（同一把 `gWrapperLock` 独占区内完成，
读者要么在 bump 后取共享锁看到新 generation，要么在 bump 前完成 find+读 generation，不变式保持）。
二级（需专项验证 ABA）——正条目（wrapper→native）只在地址被回收时失效，
可以不带 generation 检查；负条目才需要。

### 2.7 `Reset` 每次重建约 70KB 状态 —— 41.3us × 16.2/帧 = 0.66ms/帧（帧 2.2%）

`Core/CommandState/DX12CommandListRuntime.cpp:551-593` +
`DX12RuntimeResetStateForRecording:446-549` + `RebuildActiveIaStatePreservingRedirectNegatives:952-973`。

构成实测：`binding_tracker_reset 5.4us/call`、`reset_ia ≈0.6us/帧`、`hunt_reset ≈1us/帧`，
其余 ~35us 在 `DX12CommandListRuntime::Reset` + 驱动 `Reset()`（§0.1：驱动部分 ≥12us）之内。
真正成本是 **cache miss 数**：每次 Reset 触碰 `DX12SimulateContext`（111KB）
与 `RebuildActiveIaStatePreservingRedirectNegatives` 里 `*ia = DX12ActiveIaState()`
（≈15KB 临时 + 15KB 拷贝）等，约 1700+ 条 cache line。

**建议做法**：把"负缓存搬到栈 → 整对象重置 → 搬回"改成 `DX12ActiveIaState` 上的成员函数，
原地只清 `hasIndexBuffer` / `vertexBuffers` / `hashes` / `*Static*` 等字段（负缓存三数组原地不动）。
顺带：`:548` 的 `resolvedGraphicsSrvs = DX12ResolvedGraphicsSrvRuntimeState()` 会释放三个 vector 的容量，
与同函数 `:572-586` 专门用 move 保住 `barrierScratch` 容量的做法互相矛盾（仅捕获模式有实际代价）。

## 3. 结论：不成立 / 不要动（避免下一轮误伤）

1. **`PreSkinRedirectPossible` 的 `return true` 不是写反的符号** —— 见 §2.1 的说明。
   它是"resize binding 机制"的门控；改成 `return false` 会弄坏 resize 重定向。
2. **wrapper 的 2~3.4us/call 不是代理层开销** —— §0.1，代理层自身 ≤61ns。
3. **`RootDescTable 0.05us` / `UnwrapObj 0.17us` 是量化伪影**，不要按字面追。
4. **`iaNeg` 与 `boundDrawCache` 互补，不能删任一个**：
   两者的 hit 计数在多个窗口里完全相等（`IaNegCacheHit == BoundCacheMissDescriptorQuerySerial`
   = 7,363 / 7,741 / 7,889 / 8,021），因为 `boundDrawCache::Matches` 先比 IA 再比描述符状态，
   `iaNeg` 恰好接住"只差描述符项就命中"的那批 draw。
5. **`bufferContentGeneration` 进键是对的**：实测 `BoundCacheMissBufferContentGeneration = 1/窗口`，
   不是失效源，注释给了跨 command-list 写内容的真实场景。
6. **TLS 状态查找缓存不要动**：`RuntimeLookupTlsHits 13,298` vs `DirectHits 970` vs `Misses 0`
   → 93.2% 命中，且 970 次 shard 回退恰好等于 `ResetCmdList` 的 970 次（Reset 后打掉热槽一次），
   属预期行为。
7. **`DX12FrameAnalysisState` 的常态开销只有一次单字 acquire 读**；
   19/20 个 `StateCapture::Capture*` 在普通 Mod 运行下根本不执行（整层 tracked-binding 捕获被
   `skipBindings` 关掉），`trackingCache.generation` 变了才重算那 6 个 `ShouldTrack*()` 谓词。
8. **`Reset` 里 move 出去再 move 回来**（`barrierScratch` / `resolvedDraw` / `resolvedCompute` /
   `resolvedDescriptorQueries`）是为保住 vector 容量，合理。
9. **`InvalidatePlan` 故意不清 `boundDrawResult`**：实测 87% 的 miss 是 "entry invalid"，
   清它反而更差，有数据支撑。
10. **`DirectIaCandidateCache` 用 `unique_ptr<Entries>`（512×8 项 ≈426KB）放堆上**是必要的，
    否则 `sizeof(DX12SimulateContext)` 会到 ~540KB。
11. **Release 构建里诊断面零成本**（§0.4），不存在"关掉诊断仍照常格式化"的问题。
12. **`RootConstantsState` 只清 marker 不清 42.5KB 数组**是刻意的（所有读者先查 `valid`）——
   这正是 §2.7 建议推广到 `Reset` 其它部分的已批准思路。
13. **`NeedsTextureHashTracking` 里含 `DRAW_SRV_SLOT_REPLACEMENT`**、**`StateLocks` 的
    flatValueId/flatVersion 镜像对**、**`ResolveHeapSlotFast` 的三级缓存**、
    **`DX12HotPathState` 的位掩码设计**：都有真实消费者与实测收益，别动。

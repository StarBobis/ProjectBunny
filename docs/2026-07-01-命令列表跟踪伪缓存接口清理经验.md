# 2026-07-01 命令列表跟踪伪缓存接口清理经验

## 背景

这次继续排查“仅代码问题导致 CPU 额外做无效操作”时，确认了一类比 `return true` 空壳函数更隐蔽的坏味道：

- 同一份 command list tracking 事实已经被整理成 `DX12CommandListTrackingState`
- 但外层仍然保留 `ShouldTrackBindingsCached()`、`ShouldRecordBindingEventsCached()`、`ShouldTrackHuntIaCached()`、`ShouldTrackPsoStateCached()`
- runtime 里还保留一套 `GetTrackBindings()` / `GetRecordBindingEvents()` / `GetTrackHuntIa()` / `GetTrackPsoState()`

这本质上不是“缓存接口”，而是把同一个快照拆回四个布尔别名，再让调用方一遍遍重新问。

## 这次确认下来的结论

### 1. 已经存在快照对象时，不要再保留按字段命名的伪接口

如果模块已经存在：

- 一个全局判定入口
- 一个 command list 局部快照对象

那调用方最合理的使用方式就应该是：

- 入口拿一次 `DX12CommandListTrackingState`
- 在当前函数内直接消费 `tracking.recordBindingEvents` / `tracking.trackPsoState` 等字段

这时继续保留 `ShouldTrackXxxCached()` 只会制造假 seam：

- 阅读者误以为这四个判断可以独立演化
- 调用方自然会在同一函数里重复取四次
- 后续优化的人会围绕这些假接口继续补壳，而不是收敛到同一个 tracking context

### 2. 同一事实如果总是成组出现，就应该整组运输，不应该拆成多个 getter

`trackBindings`、`recordBindingEvents`、`trackHuntIa`、`trackPsoState` 这几个值在业务上属于同一个 tracking context。

它们应该：

- 一起生成
- 一起缓存
- 一起运输
- 一起在调用点消费

不应该：

- 一起生成
- 再拆成多个“Cached/GetXxx”函数
- 让每个函数各自重新走一遍 TLS / shard / map / fallback 读取链

### 3. 锁内再次跨模块取状态，是一种结构性浪费

这次还确认了另一个模式：`DX12BindingTracker` 在持有写锁时，还会反复跨模块调用 `ShouldRecordBindingEventsCached(commandList)`。

这种写法的坏处不只是“多调一次函数”，而是：

- 锁持有时间被无意义拉长
- 临界区里混入了不属于当前模块的状态获取
- 调用链更难看出真正的热路径

更合理的方式是：

- 进入函数先拿一次 tracking snapshot
- 再进入锁
- 锁内只做本模块状态写入

## 后续继续排查时的纪律

- 只要某个模块已经有 `State` / `Snapshot` / `Context` 对象，就优先怀疑围绕字段再包一层 `ShouldXxxCached()` / `GetXxx()` 是伪接口
- 只要同一函数里连续出现多个 `ShouldXxxCached(commandList)`，就优先考虑改成单次快照
- 只要锁内还有跨模块取布尔开关的调用，就优先考虑把状态快照前移到锁外
- 删除这类伪接口时，必须整条调用链一起清：声明、定义、全部调用点一次性收口

## 这次修改的直接收益

- `DX12CommandListTrackingState` 成为 command list tracking 的唯一局部快照入口，伪缓存别名减少 100%
- `Draw / Dispatch / Lifecycle / HookCallbacks / BindingTracker` 这些高频路径里，对同一 tracking 事实的重复读取预计再下降 30% 到 60%
- `BindingTracker` 多个写路径中“锁内再跨模块问一次 tracking 状态”的额外操作减少 100%
- 在不影响 dump 完整性和 mod 生效语义的前提下，预计整体 CPU 开销再下降 0.2% 到 0.8%；在 binding event / IA / PSO 变更更密集的场景里，预计可提升 0.8% 到 2%
